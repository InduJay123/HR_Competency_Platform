BTFL pillar-based review cycles

Historical implementation report. Growth-to-review linking described below was
subsequently removed; see growth-unlink-report.txt for current behavior/migrations.

1. Previous implementation
   Cycle launch immediately opened generic review forms. Both forms already had
   five pillar narratives and qualitative descriptors, but no individual targets,
   target success measures, target outcomes or Growth-to-cycle linkage existed.
   Manager responsibilities already resolve to company Head of HR. The removed
   participation stage remains absent. Dependency audit: pillar-workflow-audit.txt.

2. Architecture implemented
   New cycles default to workflow version 2. Head creates individual targets,
   saves drafts, completes all five pillars and starts the cycle. Starting fixes
   participants and notifies them. Targets can be edited with before/after audit
   history and optimistic versions until Head opens formal reviews. Opening is an
   explicit Head action; it captures targets and shared linked Growth evidence.
   It does not depend on a scheduled job. Targets then lock for all review rounds.
   One uppercase enum: CONTEXT, CHARACTER, CAPABILITY, CONTINUITY, CONTRIBUTION.
   No Accountability pillar or numeric aggregate score was added.

   Existing patterns extended:
   POST review-cycles/{id}/targets/ -- all five rows, employee, complete flag,
     per-row version (0 for a new row); drafts may contain blank target text.
   POST review-cycles/{id}/start/ -- verifies complete target setup.
   POST review-cycles/{id}/launch/ -- opens reviews for the started participants.
   GET pillar-targets/ and /{id}/ -- Head's company targets or employee's own
     completed targets; filters cycle, employee, active=true, own=true.
   Existing growth POST/PATCH accepts nullable pillar_target.
   Existing reflection/appraisal/review/AI/commitment endpoints remain canonical.
   POST reviews/{id}/pillar-evidence/ -- Head validates/excludes a captured source
     with authorised excerpt, reason, review version and immutable audit event.
   Existing review retrieval returns pillar_context; final snapshot includes it.

12. Migration/data behavior
   Add workflow_version with temporary default 1 for existing rows, then change
   model default to 2 for new cycles. This identifies the old form contract without
   inventing targets. Other new fields are null/empty for existing records.
   No business-record deletion or backfill of invented content. No production
   migrations were applied during implementation. Do not reverse these additions
   after recording targets without a full backup: reversal would remove new data.
13. Historical handling
   Existing active cycles finish using their original forms. No automatic conversion
   of existing drafts/submissions or final records. New cycles use version 2.
   FinalSnapshot hashes/content, sealed forms, review state and general audit rows
   remain unchanged. Migration tests verify original column values survive.
   New snapshots preserve target text/version, success measures, source content and
   validation, both forms with pillar outcomes/judgements, overall human assessment,
   AI history/output, commitments, acknowledgements and finalisation provenance.

14. Growth integration and privacy
   All three existing Growth tools allow optional cycle/pillar/target selection
   for the employee's own active completed targets. Unlinked entries still work.
   New links require cycle start, current cycle dates and reviews not yet opened.
   Linking never changes private/shared visibility. Only shared non-archived
   linked records are captured when formal reviews open. Later edits/unsharing
   affect living Growth records, not evidence already captured in the formal review;
   UI explains that boundary. Head validates/excludes captured sources before AI.
   AI receives only authorised excerpts, not private records or evidence URLs.
   Target setup and Growth-link writes serialize against cycle opening.

15. Before/after formal workflow
   Before: generic reflection and appraisal with separate five-pillar narratives.
   After: target setup -> cycle start -> ongoing optionally linked Growth evidence
   -> formal review opening -> five-pillar employee reflection -> five-pillar
   Head of HR appraisal -> AI coaching -> shared commitments -> acknowledgements
   -> Head finalisation -> locked final record.
   Appraisal submission requires employee submission. Each pillar uses the existing
   Exceptional / Strong / Developing / Needs Attention vocabulary and a separate
   Not achieved / Partially achieved / Achieved / Exceeded target outcome.
   Overall uses existing Steward descriptors and a human rationale, not averaging.
   AI is advisory; prompt version v3 explicitly compares targets and both accounts.
   Commitments unlock directly after completed AI; the six-step progress display
   has no participation stage. Source validation and existing evidence safeguards
   remain prerequisites for AI/finalisation, not a new progress stage.
